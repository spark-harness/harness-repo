# 数据库规范

本文适用于业务服务的数据表、迁移、查询和数据修复。

它不是 DBA 手册，也不替代具体服务的数据设计。服务级表结构和历史经验写到 `context/project/`。

## 最小规则

| 主题 | 规则 |
|---|---|
| Migration | schema 变化必须通过可追溯 migration，不手工改库 |
| 回滚 | 高风险 migration 必须说明回滚或止血方案 |
| 索引 | 新查询条件、唯一约束和排序分页必须评估索引 |
| 事务 | 事务范围围绕业务一致性，不把慢外部调用放进事务 |
| 分页 | 列表接口必须有稳定排序，禁止无界查询 |
| 时间 | 表中时间字段使用统一时区和命名，避免混用本地时间 |
| 审计 | 关键状态变化保留创建/更新/操作者或等价审计字段 |
| 数据修复 | 修复脚本必须可审查、可回滚或可重复执行 |

## Migration 检查

提交数据库变更前确认：

- migration 文件和业务代码在同一 ticket 中可追溯。
- DDL 是否阻塞写入或长时间锁表。
- 新字段是否需要默认值、回填或双写兼容。
- 删除字段或表是否有历史读取方。
- 回滚方案是否现实。

## 查询和索引

- 高频查询必须说明过滤条件、排序字段和预期数据量。
- 唯一业务约束优先落到数据库唯一索引或等价机制。
- 复合索引顺序必须匹配主要查询路径。
- 禁止为了“可能会查”提前加大量低价值索引。

## 事务和并发

- 幂等键、唯一约束、状态机和锁要一起设计。
- 不依赖“先查再写”避免并发冲突，必须有数据库约束或原子更新。
- 悲观锁、乐观锁和唯一约束的选择必须写清业务原因。

## 数据修复

数据修复必须记录：

- 修复对象和筛选条件。
- 预估影响行数。
- 执行前备份或查询证据。
- 幂等性。
- 回滚方式。
- 执行人和执行时间。

## 设计门禁检查

涉及数据库时，设计至少说明：

- 表、字段、索引或 migration 是否变化。
- 是否需要回填、双写或兼容读取。
- 是否影响事务、锁、分页、慢查询。
- 是否需要数据修复或运营脚本。
