# 指标规范

指标用于观察系统和业务在一段时间内的趋势、容量、错误和健康状态。

## 它不是什么

指标不是日志的替代品。

日志回答“某个点发生了什么”，Tracing 回答“一次请求经过了哪里”，指标回答“整体是否正常、趋势是否恶化、容量是否接近边界”。

指标也不是业务数据库。不要依赖指标保存订单状态、支付流水、审计证据或需要精确对账的数据。

## 它是什么

指标用于回答：

- 服务是否可用。
- 请求量是否异常。
- 错误率是否升高。
- 延迟是否恶化。
- 下游依赖是否不稳定。
- 队列、任务、缓存、数据库是否接近容量或积压边界。
- 核心业务漏斗、资金链路或履约链路是否出现异常趋势。

团队指标应优先基于 OpenTelemetry Metrics 或兼容规范暴露，并与日志、Tracing 通过 `service.name`、环境和稳定业务维度关联。

## 基础要求

- `service.name` 必须与服务矩阵中的服务名一致。
- 指标名称必须稳定、低歧义、可聚合。
- 标签必须低基数，不能把用户 ID、订单 ID、手机号、请求体摘要等放入高频标签。
- 错误指标必须能关联稳定错误码或错误类别。
- 关键外部调用必须有请求量、错误率和延迟指标。
- 关键异步链路必须有生产、消费、失败、重试和积压指标。
- 关键业务链路必须有业务结果指标，而不只看接口成功率。

## 指标类型

| Type | 用途 | 示例 |
|---|---|---|
| Counter | 只增不减的累计次数 | 请求总数、失败总数、消息消费总数 |
| Gauge | 当前瞬时值 | 队列积压、活跃连接数、库存水位 |
| Histogram | 分布和分位数 | 请求延迟、下游调用耗时、任务处理耗时 |

不要用 Gauge 表示累计次数，也不要用 Counter 表示当前库存、余额或队列深度。

## 命名

指标命名应表达对象和度量内容。

推荐格式：

```text
{domain_or_component}.{object}.{measure}
```

示例：

```text
http.server.requests
rpc.client.duration
order.checkout.requests
payment.channel.failures
inventory.reserve.duration
message.consumer.lag
```

命名要求：

- 使用稳定业务域或技术组件名。
- 不把用户 ID、订单 ID、日期、版本号放进指标名。
- 不在指标名中编码动态状态，状态应放在受控标签中。
- 同一类指标在不同服务中使用一致命名。

## 标签

标签用于聚合和筛选，但必须控制基数。

推荐标签：

| Label | 含义 | 示例 |
|---|---|---|
| `service.name` | 服务名 | `order-api` |
| `deployment.environment` | 环境 | `prod`、`staging` |
| `operation` | 稳定操作名 | `CreateOrder` |
| `method` | HTTP 或 RPC 方法 | `POST`、`CreateOrder` |
| `route` | 模板化路由 | `/orders/{id}` |
| `status_code` | 协议状态码 | `200`、`500` |
| `error_code` | 稳定错误码 | `ORDER-STATE-0001` |
| `dependency` | 下游依赖名 | `payment-api` |
| `channel` | 受控渠道名 | `wechat_pay` |

禁止作为高频标签：

- 用户 ID、订单 ID、设备 ID、手机号、身份证、银行卡。
- 原始 URL、原始 query、请求体、响应体。
- 异常堆栈、错误文案、动态 SQL。
- 未受控的外部渠道返回码。

如果必须按高基数对象排障，应优先使用日志或 trace，并通过采样、脱敏和访问控制处理。

## RED 指标

同步请求链路应至少覆盖 RED 指标。

| Metric | 含义 |
|---|---|
| Rate | 请求量或吞吐 |
| Errors | 失败量、错误率、错误码分布 |
| Duration | 延迟分布和关键分位数 |

适用范围：

- HTTP API。
- gRPC API。
- 内部 RPC。
- 外部渠道调用。
- 数据库和缓存访问。

关键接口应至少能查看 `p50`、`p90`、`p95` 或 `p99` 延迟。具体分位数按服务风险和流量规模选择，但设计中必须说明关注哪个延迟指标。

## USE 指标

资源和容量类对象应优先覆盖 USE 指标。

| Metric | 含义 |
|---|---|
| Utilization | 使用率 |
| Saturation | 饱和度或排队程度 |
| Errors | 资源错误或拒绝次数 |

适用范围：

- CPU、内存、磁盘、网络。
- 连接池、线程池、协程池。
- 数据库连接、缓存连接。
- 队列积压、任务池积压。

资源指标用于容量判断，不应替代业务成功率和错误率指标。

## 业务指标

关键业务链路必须有业务结果指标。

示例：

| Domain | 推荐指标 |
|---|---|
| 订单 | 创建成功数、取消数、状态流转失败数 |
| 支付 | 发起数、成功数、失败数、渠道超时数、回调延迟 |
| 库存 | 预占成功数、释放数、扣减失败数 |
| 结算 | 结算任务数、失败数、重试数、差异数 |
| 权限 | 拒绝数、鉴权失败数、异常放行数 |

业务指标必须能回答业务结果是否正确，不能只看 API 返回成功。

例如支付接口返回成功但回调长期未到达时，接口成功率不能代表支付链路健康。

## 异步指标

消息、任务和事件链路必须观察生产和消费两侧。

最低指标：

- 生产成功数和失败数。
- 消费成功数和失败数。
- 消费延迟。
- 重试次数。
- 死信数量。
- 积压数量或 lag。
- 幂等冲突数量。

异步链路的错误率应区分可重试失败、不可重试失败和业务拒绝，避免把正常幂等冲突误判为系统故障。

## 外部依赖指标

调用外部服务或第三方渠道时，必须记录依赖维度。

最低指标：

- 调用次数。
- 成功次数和失败次数。
- 超时次数。
- 限流或拒绝次数。
- 延迟分布。
- 重试次数。
- 熔断、降级或回退次数。

外部渠道返回码不能直接作为无限制标签。应先映射成受控错误类别、错误码或渠道结果分类。

## 告警

告警应基于用户影响、业务影响或明确容量风险。

推荐告警对象：

- 核心接口错误率持续升高。
- 核心接口延迟超过 SLO。
- 关键业务成功率下降。
- 支付、结算、履约、库存等核心链路积压。
- 下游依赖超时、拒绝或熔断持续升高。
- 死信数量持续增加。
- 资源饱和导致请求失败或任务积压。

不推荐告警：

- 单次请求失败。
- 无用户影响的瞬时抖动。
- 没有处理动作的低价值指标。
- 无 owner、无阈值依据、无恢复路径的告警。

每条阻塞级告警必须能说明：

- 影响范围。
- 判断阈值。
- 责任人或责任团队。
- 排查入口。
- 临时止血或回滚动作。

## SLO

核心服务和关键链路应定义 SLO。

SLO 应至少说明：

- 目标对象，例如接口、任务、业务链路。
- 目标窗口，例如 5 分钟、1 小时、30 天。
- 成功定义。
- 延迟目标。
- 错误预算或允许失败范围。
- 超出目标后的处理动作。

没有用户或业务影响的内部指标，不应强行定义高成本 SLO。

## 采样与保留

指标默认用于聚合趋势，应控制采集成本。

要求：

- 高频指标必须控制标签基数。
- 直方图 bucket 应按业务延迟目标设置，不能只使用默认值。
- 关键业务指标保留周期应能支持事故复盘和趋势分析。
- 调试型临时指标必须有清理计划。
- 不把敏感信息写入指标名、标签和值。

## 设计门禁检查

如果需求新增或修改关键链路，设计门禁必须检查：

- 是否定义需要新增或修改的技术指标和业务指标。
- 是否覆盖请求量、错误率、延迟或对应异步指标。
- 是否说明标签集合，并确认没有高基数或敏感标签。
- 是否说明错误码、日志和 trace 如何与指标关联。
- 是否说明关键外部依赖的指标。
- 是否说明业务成功率或最终业务结果如何观察。
- 是否需要新增或调整告警、SLO、仪表盘。
- 是否评估指标量和采集成本。

## 合并前检查

合并前必须确认：

- 指标名称和标签稳定。
- 新增错误路径有错误计数或错误码分布。
- 关键延迟指标使用合适的 Histogram。
- 关键异步链路可以观察积压、失败、重试和死信。
- 告警有 owner、阈值依据和处理动作。
- 仪表盘或查询入口已记录到门禁报告或项目现状文档。
