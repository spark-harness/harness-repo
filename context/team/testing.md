# 测试规范

测试用于证明业务行为可信，不用于证明代码被执行过。

## 它不是什么

测试不是覆盖率数字的附属品。

覆盖率不是质量目标本身。为了覆盖率给 getter、setter、框架生成代码、简单转发方法或无业务分支的样板代码补测试，通常不能发现有意义的问题，反而会增加维护成本。

测试也不是实现细节的锁定工具。测试不应优先验证某个内部方法被调用几次、某个 mock 是否收到调用，而应验证业务输入经过系统处理后产生的业务结果。

## 它是什么

测试用于验证：

- 核心业务规则是否正确。
- 关键边界和异常路径是否可控。
- 模块协作是否符合契约。
- 完整业务链路是否满足用户可见行为。
- 变更是否没有破坏既有能力。

有效测试应围绕业务行为组织，而不是围绕覆盖率指标、代码结构或临时实现细节组织。

## 分层

不同层级的测试解决不同问题，不能互相替代。

| Layer | 目标 | 典型范围 | 不应包含 |
|---|---|---|---|
| 单元测试 | 验证独立业务逻辑在稳定输入下产生预期输出 | 单个类、方法、纯业务规则、独立行为路径 | 数据库、容器、外部服务、真实网络 |
| 集成测试 | 验证模块之间协作是否正确 | controller、service、repository、数据库、消息组件 | 完整用户操作链路 |
| 端到端测试 | 从用户或外部系统视角验证完整业务结果 | 下单、支付、转账、放款等完整链路 | 细碎实现分支 |

如果测试需要访问数据库、启动容器、调用外部服务或依赖真实中间件，它不应被归类为单元测试。

## 单元测试

单元测试应聚焦稳定、可隔离、可快速反馈的业务逻辑。

适合写单元测试的对象：

- 金额、费率、折扣、库存、状态机等核心计算或判断逻辑。
- 明确输入和输出的领域规则。
- 高风险边界条件。
- 明确异常路径。

不优先写单元测试的对象：

- 只有 getter、setter 或简单字段赋值的代码。
- 框架自动生成或由框架保证的代码。
- 没有业务分支的简单透传方法。
- 只能通过大量 mock 才能勉强隔离的遗留胶水代码。

单元测试通常应快速执行。单个测试如果需要明显等待外部资源，应重新判断它是否属于集成测试。

## 集成测试

集成测试用于验证模块协作，而不是补单元测试覆盖率。

适合写集成测试的场景：

- API 层到应用层、领域层、仓储层之间的协作。
- 数据库映射、事务边界、唯一约束和查询条件。
- 消息发布、消费和幂等处理。
- 缓存、配置、权限、错误码和日志字段是否在真实路径中生效。
- protobuf、HTTP 或外部接口适配层是否符合契约。

集成测试应优先覆盖容易在模块边界出错的路径，而不是重复验证已经由单元测试覆盖的纯计算逻辑。

## 端到端测试

端到端测试用于证明完整业务链路从用户或外部系统视角可用。

适合写端到端测试的场景：

- 核心收入、资金、履约、权限、风控链路。
- 多服务协作后产生最终业务状态的流程。
- 发布前必须证明没有破坏的关键回归场景。

端到端测试数量应受控。它不适合覆盖所有分支，而应覆盖最高价值、最高风险的业务路径。

## 命名

测试命名必须让评审者能看出测试目标、场景和预期结果。

单元测试方法推荐格式：

```text
{method}_{scenario}_{expectedResult}
```

示例：

```text
transfer_withValidAmount_shouldDeductSourceBalance
calculateInterest_withLeapYear_shouldUseActualDays
```

单元测试类推荐以 `Test` 结尾：

```text
AccountServiceTest
InterestCalculatorTest
```

集成测试方法推荐格式：

```text
{feature}_{componentInteraction}_{verificationPoint}
```

集成测试类推荐以 `IT` 或 `IntegrationTest` 结尾：

```text
TransferServiceRepositoryIT
OrderPaymentIntegrationTest
```

端到端测试应使用用户或业务语言描述：

```text
用户转账_成功转账1000元_双方余额正确
```

端到端测试类推荐以 `E2ETest` 结尾：

```text
FundTransferE2ETest
CheckoutPaymentE2ETest
```

## 结构

单个测试应遵循 AAA 结构：

| Step | 作用 |
|---|---|
| Arrange | 准备测试数据和依赖 |
| Act | 执行被测行为 |
| Assert | 验证业务结果 |

测试必须有明确断言。不能把“不报错”当作默认成功。

异常场景也必须明确断言：

- 断言抛出了预期异常。
- 断言错误码正确。
- 断言业务状态没有被错误修改。
- 断言需要保留的审计、日志、事件或补偿记录存在。

## FIRST 原则

单元测试应满足 FIRST 原则：

| Principle | 要求 |
|---|---|
| Fast | 快速执行，开发者愿意频繁运行 |
| Isolated | 测试之间互不依赖，不依赖执行顺序 |
| Repeatable | 在本地、CI 和不同环境重复执行结果一致 |
| Self-Validating | 通过断言自动判断成功或失败，不依赖人工看日志 |
| Timely | 与业务代码同步编写，必要时先于实现编写 |

如果测试不稳定、依赖顺序或需要人工判断，它不能作为有效门禁证据。

## 行为驱动

测试应验证“做什么”，而不是锁定“怎么做”。

推荐验证：

- 转账成功后，转出账户余额减少，转入账户余额增加。
- 含税价格计算结果符合税率和舍入规则。
- 订单终态不可修改，并返回稳定错误码。
- 支付渠道超时后进入可重试状态。

不推荐验证：

- 某个内部 `update` 方法被调用一次。
- 某个私有步骤按当前实现顺序执行。
- 某个 mock 收到与业务结果无关的调用。

过度 mock 会让测试绑定实现细节。只要业务结果可以通过真实领域对象、轻量 fake 或集成测试验证，就不应优先用大量 mock 验证内部调用。

## 覆盖重点

测试资源应优先投入高风险、高价值业务。

优先覆盖：

- 资金、订单、库存、权限、风控、结算等核心领域。
- 状态流转和不可逆操作。
- 金额、币种、舍入、分摊、汇率等资金规则。
- 幂等、重试、并发、超时和补偿。
- 兼容性、错误码和用户可见失败语义。

可以放宽：

- 页面样式细节。
- 日志格式的非关键字段。
- 简单参数序列化。
- 无业务分支的样板代码。

边界测试和异常测试不能喧宾夺主。它们应优先服务核心业务模块，而不是为了覆盖率堆在低风险辅助代码上。

## 覆盖率

覆盖率只能作为辅助信号，不能作为单独的质量结论。

覆盖率使用规则：

- 覆盖率下降需要解释原因。
- 高风险模块可以设置更高覆盖要求。
- 低风险样板代码不应为了覆盖率强行补测试。
- 覆盖率达标但核心业务场景缺失时，门禁不能通过。
- 覆盖率报告必须结合测试清单、失败路径和验收证据一起评审。

团队评审时应优先问：

- 核心业务行为是否被验证。
- 最容易出错的边界是否被覆盖。
- 失败路径是否有明确断言。
- 测试失败是否能指出真实业务风险。

## 遗留系统

遗留系统不能机械套用新系统的单元测试标准。

当系统耦合严重、业务逻辑散落在框架层或全局状态中时，为了追求纯隔离单元测试而大规模重构，可能带来更高风险。

遗留系统推荐策略：

- 对核心计算和规则模块补少量高价值单元测试。
- 对模块协作补中等规模集成测试。
- 对关键业务流程补适量端到端测试。
- 在重构前先用测试锁定现有业务行为。
- 不为低价值代码补覆盖率型测试。

遗留系统测试目标是风险可控，不是形式完美。

## 设计门禁检查

如果需求新增或修改业务逻辑，设计门禁必须检查：

- 是否说明需要哪些单元测试、集成测试和端到端测试。
- 是否优先覆盖核心业务行为，而不是只追求覆盖率。
- 是否列出关键边界和异常路径。
- 是否避免用 mock 锁死实现细节。
- 是否定义错误码、状态变化、金额规则、幂等和并发场景的验证方式。
- 是否说明遗留系统中无法补单元测试时的替代测试策略。
- 是否说明测试证据保存位置。

## 合并前检查

合并前必须确认：

- 新增或修改的核心业务行为有测试覆盖。
- 失败路径有明确断言，不依赖人工查看日志。
- 测试可以在 CI 中重复执行。
- 不稳定测试已修复、隔离或明确移出阻塞门禁。
- 覆盖率变化有解释，但不以覆盖率替代业务测试结论。
- 涉及多仓或契约变更时，相关仓库的测试和契约检查都有结果记录。
