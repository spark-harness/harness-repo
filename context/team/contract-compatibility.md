# 契约兼容性规范

契约兼容性用于保证服务、客户端、任务和外部系统可以在不同版本之间平滑协作。

## 它不是什么

契约兼容性不是只让代码编译通过。

生成代码成功、单元测试通过、接口在本地能调通，都不能单独证明契约兼容。真正的兼容性要考虑已经发布的调用方、灰度中的服务、历史消息、缓存数据和外部系统。

契约兼容性也不是只检查 protobuf breaking change。HTTP JSON、错误码、事件、配置、数据库外部可见语义和用户可见字段，都是契约的一部分。

## 它是什么

契约是服务边界上的稳定承诺。

团队需要管理的契约包括：

- protobuf message、service、rpc、field、enum。
- HTTP path、method、query、header、request body、response body。
- 错误码、错误语义、可重试语义和用户可见失败策略。
- 事件、消息、任务 payload 和 topic。
- 回调、webhook 和外部渠道适配字段。
- 对前端、客户端、运营、客服和数据系统可见的字段语义。

契约变更必须能说明：

- 谁会消费这个契约。
- 新旧版本是否可以同时存在。
- 调用方如何灰度升级。
- 回滚时旧版本是否还能工作。
- 是否需要同步更新需求、设计、门禁和项目现状知识。

## 基础原则

- 默认保持向后兼容。
- 已发布契约不得静默改变语义。
- 删除、重命名、改类型、改单位、改默认值都按高风险处理。
- 新增字段必须说明默认语义。
- 调用方不能被要求和服务方同时发布才能正常工作，除非设计文档明确说明发布编排和回滚策略。
- 兼容性结论必须有检查证据，不能只写“无影响”。

## Protobuf 兼容性

protobuf 契约变更必须优先遵守 buf v2 检查要求。

允许的低风险变更：

- 新增 optional 语义字段，并定义缺省行为。
- 新增 request 字段，但服务端不能强制旧客户端必须传。
- 新增 response 字段，但旧客户端忽略后不影响原有行为。
- 新增 rpc，且不改变已有 rpc 语义。
- 新增 enum 值，并确认旧消费者遇到未知值时有安全处理。

高风险或禁止变更：

- 删除已发布字段。
- 复用已删除字段编号或字段名。
- 修改字段编号。
- 修改字段类型。
- 修改字段单位，例如从主单位金额改成最小货币单位。
- 修改字段含义，例如把 `status` 从订单状态改成支付状态。
- 修改 rpc request 或 response 的业务语义。
- 把原本可选的字段变成事实必填。
- 删除 enum 值或改变 enum 值含义。

删除字段时必须保留编号和名称：

```proto
message Example {
  reserved 3;
  reserved "old_field";
}
```

字段废弃应优先使用废弃策略，而不是直接删除：

```proto
message Example {
  string old_field = 3 [deprecated = true];
  string new_field = 4;
}
```

废弃字段在所有已知消费者完成迁移前，不得删除。

## HTTP / JSON 兼容性

HTTP 接口兼容性不只看 path 是否存在，还要看请求、响应和错误语义。

允许的低风险变更：

- 新增可选 request 字段，并定义未传时行为。
- 新增 response 字段，旧客户端忽略后不影响原有逻辑。
- 新增 query 参数，未传时保持旧行为。
- 新增错误码，但旧客户端已有兜底处理。

高风险或禁止变更：

- 删除 response 字段。
- 改变字段类型，例如 string 改 number。
- 改变金额、时间、枚举、状态字段的单位或语义。
- 把非必填 request 字段改成必填。
- 改变 HTTP status 与业务错误码映射。
- 改变分页、排序、过滤默认行为。
- 在不改版本或不说明兼容策略的情况下修改 path 语义。

JSON 金额字段必须遵守金额规范。金额不应从 decimal string 静默改成 number，也不应把内部主单位改成渠道最小货币单位。

## 错误码兼容性

错误码是契约，不是日志文案。

错误码变更必须遵守：

- 已发布错误码不得复用。
- 已发布错误码不得改成不同含义。
- 可重试语义变化必须评估调用方重试、告警和客服处理影响。
- 用户可见错误策略变化必须评估前端、客户端和运营话术。
- 新增错误码必须更新错误码表或对应领域文档。

如果旧错误码语义不再适用，应废弃旧错误码并新增错误码，不能直接改旧码含义。

## 事件与消息兼容性

事件和消息可能被异步、延迟、重试或批量消费，因此兼容性要求比同步接口更严格。

事件变更必须考虑：

- 历史消息是否仍可能被消费。
- 新旧消费者是否会同时存在。
- 消费端遇到未知字段、未知 enum 或缺失字段时是否安全。
- topic、event type、schema version 是否稳定。
- 幂等 key、业务主键和去重语义是否变化。
- 死信和重放是否能处理新旧 payload。

高风险变更：

- 改变 event type 含义。
- 删除消费者依赖字段。
- 修改幂等 key。
- 修改事件顺序假设。
- 把一个事件拆成多个事件但没有说明消费端迁移策略。
- 合并多个事件导致旧消费者无法区分业务语义。

事件 payload 推荐显式携带版本字段。版本字段只能用于兼容演进，不能作为绕过契约治理的理由。

## 兼容性策略

常见兼容性策略包括：

| Strategy | 适用场景 | 要求 |
|---|---|---|
| Additive change | 新增字段、新增接口、新增 enum | 旧消费者忽略后仍正确 |
| Deprecate then remove | 字段或接口需要下线 | 先标记废弃，确认消费者迁移，再删除 |
| Dual write | 新旧字段、事件或存储并行 | 明确一致性校验和停止条件 |
| Dual read | 同时读取新旧字段或格式 | 明确优先级和回退策略 |
| Versioned endpoint | 语义无法兼容 | 新旧版本并行，定义迁移窗口 |
| Adapter mapping | 外部渠道语义不同 | 在适配层转换，不污染内部契约 |

设计文档必须选择具体策略。不能只写“兼容旧版本”。

## 发布顺序

多仓或多服务契约变更必须说明发布顺序。

推荐顺序：

1. 发布可兼容旧调用方的服务端变更。
2. 发布契约仓变更和生成物。
3. 发布新调用方。
4. 观察新旧版本并行指标和错误码。
5. 完成迁移后，再废弃旧字段、旧接口或旧事件。

如果必须先发布调用方，设计文档必须说明服务端旧版本如何安全处理新请求，或者如何通过配置、灰度和回滚控制风险。

## 回滚

契约变更必须能解释回滚后的行为。

回滚检查：

- 服务端回滚后，已经发布的新客户端是否还能工作。
- 客户端回滚后，新服务端是否还能兼容旧请求。
- 已写入的新字段、新状态、新事件是否会让旧代码无法读取。
- 消息重放、补偿任务和定时任务是否能处理新旧格式。
- 外部渠道或第三方回调是否会继续发送新字段或新状态。

如果回滚不能兼容，必须在设计中标记为高风险，并给出灰度、开关、数据修复或人工处理方案。

## 检查证据

涉及 protobuf 的变更必须记录：

```text
buf lint
buf generate
buf breaking --against '.git#branch=main'
```

涉及 HTTP / JSON 的变更应记录：

- 接口差异说明。
- 新旧请求样例。
- 新旧响应样例。
- 错误码变化。
- 调用方清单和迁移状态。

涉及事件或消息的变更应记录：

- topic 或 event type。
- payload 差异。
- schema version。
- 新旧消费者兼容结论。
- 重放和死信处理结论。

## 设计门禁检查

如果需求新增或修改契约，设计门禁必须检查：

- 是否列出所有受影响调用方和消费者。
- 是否说明变更属于新增、废弃、删除、重命名、改类型还是改语义。
- 是否选择明确兼容性策略。
- protobuf 是否完成 buf lint、generate 和 breaking 检查。
- HTTP / JSON 是否提供新旧请求和响应样例。
- 错误码变化是否遵守错误码规范。
- 事件或消息是否能处理历史 payload 和新旧消费者并存。
- 发布顺序和回滚策略是否可执行。
- 是否需要更新服务矩阵、需求、设计、错误码表或项目现状知识。

## 合并前检查

合并前必须确认：

- 契约仓、业务仓和 Harness 仓变更可以互相追溯。
- 兼容性检查证据已写入门禁报告。
- breaking change 已被识别，并有明确版本、灰度和回滚方案。
- 已发布字段编号、字段名、错误码和事件类型没有被复用。
- 新旧版本并行期间的监控、日志和错误码能定位问题。
- 所有关联消费者都有迁移计划或明确不受影响的证据。
