# 日志与可观测性规范

日志和指标用于定位业务问题，不用于堆叠实现细节。

## 它不是什么

日志不是业务数据库，不是审计系统，也不是埋点和指标的替代品。

不要依赖日志保存关键业务状态。关键状态必须落到业务存储或事件系统。

## 它是什么

日志用于回答：

- 请求从哪里来。
- 经过了哪个服务和操作。
- 关键业务对象是什么。
- 为什么失败。
- 如何关联上下游链路。

## 最低要求

- 关键业务状态变化应有可检索日志。
- 跨服务调用应保留请求标识或链路标识。
- 错误日志应包含错误码或稳定错误类型。
- 不记录明文密钥、令牌、身份证、银行卡等敏感信息。

## 日志级别

| Level | 使用场景 |
|---|---|
| `DEBUG` | 本地排查或临时灰度诊断，默认不应在线上长期打开 |
| `INFO` | 关键业务路径、状态变化、重要外部调用结果 |
| `WARN` | 可恢复异常、降级、重试、非预期但不影响主流程的问题 |
| `ERROR` | 请求失败、任务失败、数据不一致、下游不可用等需要处理的问题 |

## 结构化字段

所有服务应优先输出结构化日志。推荐字段：

| Field | 含义 | 必填 |
|---|---|---:|
| `timestamp` | 日志时间 | Yes |
| `level` | 日志级别 | Yes |
| `service` | 服务名 | Yes |
| `operation` | 操作名或 RPC 方法 | Yes |
| `trace_id` | 链路 ID | Yes |
| `span_id` | 当前 span ID | Yes |
| `request_id` | 请求 ID | Yes |
| `user_id` | 用户标识，按安全规范脱敏 | No |
| `resource_id` | 业务对象 ID | No |
| `error_code` | 稳定错误码 | 失败时必填 |
| `latency_ms` | 耗时 | 外部调用必填 |

示例：

```json
{
  "level": "ERROR",
  "service": "order-api",
  "operation": "CreateOrder",
  "trace_id": "trace-001",
  "span_id": "span-001",
  "request_id": "req-001",
  "resource_id": "order-123",
  "error_code": "ORDER-STATE-0001",
  "message": "order state does not allow update"
}
```

## 禁止记录

- 明文密码、密钥、令牌、Cookie、Authorization header。
- 身份证、银行卡、手机号等敏感信息原文。
- 大体积请求体或响应体。
- 无采样控制的循环日志。
- 只对开发者有意义但无法排障的临时变量堆叠。

## 设计检查

如果需求新增关键链路，设计文档应说明日志、指标、追踪或事件的变化。

设计门禁至少检查：

- 新增失败路径是否有错误码。
- 关键外部调用是否记录耗时和下游结果。
- 跨服务链路是否能通过 `trace_id` 或 `request_id` 串起来。
- 是否与 OpenTelemetry trace 关联，日志中是否包含 `trace_id` 和 `span_id`。
- 敏感字段是否脱敏。
- 日志量是否可能在高峰期放大。
