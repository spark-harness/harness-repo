# 安全与敏感信息规范

本文适用于需求、设计、代码、测试、日志、门禁报告和知识文档。

它不是完整安全基线，也不替代安全评审。第一版只定义团队开发和评审时必须守住的边界。

## 最小规则

| 主题 | 规则 |
|---|---|
| Secret | 不在仓库、需求、设计、门禁报告或知识文档中保存真实密钥 |
| 示例数据 | 示例手机号、身份证、银行卡、邮箱、地址必须脱敏或伪造 |
| 日志 | 不记录 token、Cookie、Authorization、密码、证件号、银行卡原文 |
| 权限 | 新增或修改权限边界必须在设计中说明主体、资源和动作 |
| 输入 | 外部输入必须校验格式、长度、范围和业务合法性 |
| 输出 | API、页面和日志不得暴露内部异常、堆栈、SQL 或敏感字段 |
| 依赖 | 新增第三方服务或 SDK 必须说明数据出境、密钥和失败处理 |

## Secret 管理

- 只提交变量名、用途和示例占位值。
- 本地 `.env`、证书、私钥和 token 不得提交。
- CI/CD secret 只通过平台 secret 管理，不写进脚本参数或日志。
- 密钥泄漏后不能只删除提交，必须轮换密钥并记录处理结果。

## 权限检查

涉及权限时，设计必须回答：

- 谁可以执行这个动作？
- 操作哪个资源？
- 是否需要租户、用户、角色或状态约束？
- 拒绝访问时返回什么稳定错误？
- 是否需要审计日志？

## 敏感字段

常见敏感字段包括：

- 认证凭证：password、token、secret、Cookie、Authorization。
- 个人信息：手机号、身份证、邮箱、地址、银行卡。
- 风控和授信信息。
- 内部系统地址、密钥路径、供应商凭证。

需要排障时，优先记录脱敏后缀、hash 或内部追踪 ID。

## 门禁要求

设计门禁发现安全风险时，应记录为 `BLOCKED` 或 `WARN`，并写明责任人和后续动作。

合并前必须确认：

- 没有新增真实 secret。
- 日志、指标、trace 不包含敏感原文。
- 权限、输入校验和错误输出已覆盖。
- 高风险安全问题有明确 owner 和处理计划。
