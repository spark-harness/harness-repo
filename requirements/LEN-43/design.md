## Summary

本设计把 LEN-2 手机验证链路接入到 `fides-bff`。方案不是把 applicant 业务规则复制进 BFF，而是让 BFF 成为前端协议边界：`fides` 调 BFF REST，BFF 按 BFF-facing proto 解析请求并调用 applicant-api gRPC，最后把 applicant 错误和会话结果映射回前端。

设计重点有三个：

- 契约事实源：BFF auth proto 必须带 HTTP 注解，避免手写 REST 路由和 gRPC 语义漂移。
- 运行时边界：`fides-bff` 只做协议、幂等、错误、trace 和服务发现，不保存 OTP 状态。
- 可回滚接入：`fides` 继续保留 mock / disabled / real adapter mode，通过环境配置切换真实 BFF。

## API / Contract Design

- Protobuf IDL required: Yes.
- Proto file: `idl-repo/vesta/lendora/fides-bff/v1/auth.proto`.
- Buf module: `local/lendora-fides-bff`.
- Buf config version: v2.
- Generated outputs:
  - Go message and gRPC stubs under existing `github.com/spark-harness/idl-go-repo`.
  - Java output may be generated by global template but is not a runtime consumer for LEN-43.
- Breaking check baseline: `buf breaking --against .git#branch=master`.
- Compatibility strategy: additive new service/RPC/message, no existing consumer break.
- Lint exception: because the approved source path is `vesta/lendora/fides-bff/v1/auth.proto` but protobuf package segments cannot contain `-`, `buf.yaml` carries a targeted `PACKAGE_DIRECTORY_MATCH` exception for this file only. The proto package remains `vesta.lendora.fides_bff.v1`.

Target proto shape:

```proto
syntax = "proto3";

package vesta.lendora.fides_bff.v1;

import "google/api/annotations.proto";

option go_package = "github.com/spark-harness/idl-go-repo/vesta/lendora/fides-bff/v1;fidesbffv1pb";
option java_multiple_files = true;
option java_outer_classname = "FidesBffAuthProto";
option java_package = "com.vesta.lendora.fidesbff.v1";

service FidesBffAuthService {
  rpc SendOtp(SendOtpRequest) returns (SendOtpResponse) {
    option (google.api.http) = {
      post: "/api/v1/auth/otp:send"
      body: "*"
    };
  }

  rpc VerifyOtp(VerifyOtpRequest) returns (VerifyOtpResponse) {
    option (google.api.http) = {
      post: "/api/v1/auth/otp:verify"
      body: "*"
    };
  }

  rpc RefreshToken(RefreshTokenRequest) returns (RefreshTokenResponse) {
    option (google.api.http) = {
      post: "/api/v1/auth/token:refresh"
      body: "*"
    };
  }
}
```

Message model:

| Message | Fields | Source / Target |
|---|---|---|
| `SendOtpRequest` | `country_code`, `phone` | From fides request body; idempotency key stays HTTP header and is copied into applicant request by BFF |
| `SendOtpResponse` | `challenge_id`, `expires_in_sec`, `resend_after_sec` | From applicant-api |
| `VerifyOtpRequest` | `challenge_id`, `code` | From fides request body; idempotency key from HTTP header |
| `VerifyOtpResponse` | `access_token`, `refresh_token`, `applicant_id`, `expires_in_sec`, `refresh_expires_in_sec` | From applicant-api |
| `RefreshTokenRequest` | `refresh_token` | From fides request body; idempotency key from HTTP header |
| `RefreshTokenResponse` | `access_token`, `expires_in_sec` | From applicant-api |

`Idempotency-Key` 不放入 BFF-facing request body。原因是它是横切 HTTP header，已有 `bffkit.IdempotencyFilter` 负责读取和回放；BFF service 再从 request context/header 取值并填入 applicant-api gRPC request，避免前端 body 与 header 双来源冲突。

## BFF Application Design

目录保持 LEN-21 Kratos + Clean Architecture 形状：

```text
services/backend/fides-bff/
├── internal/biz/auth.go
├── internal/service/auth.go
├── internal/data/applicant_auth_client.go
├── internal/data/consul_resolver.go
├── internal/conf/conf.go
└── internal/server/http.go
```

职责划分：

- `internal/biz`
  - 定义 `AuthUsecase`。
  - 定义 `ApplicantAuthClient` port。
  - 定义 `SendOtpCommand`、`VerifyOtpCommand`、`RefreshTokenCommand` 和结果类型。
  - 不 import generated proto、HTTP、Consul 或 gRPC transport 实现。
- `internal/service`
  - 实现 BFF-facing auth service / REST handler。
  - 将 generated BFF proto DTO 映射到 `biz` command。
  - 从 request context 读取 `Idempotency-Key` 和 trace metadata。
  - 将 `biz` 结果映射为 generated BFF proto response。
- `internal/data`
  - 实现 applicant-api gRPC client。
  - 通过 Consul resolver 生成 gRPC target。
  - 将 applicant generated proto response 映射回 `biz` 结果。
  - 将 applicant gRPC status / error detail 转换为 `biz` 或 `bffkit` 可编码错误。
- `internal/server`
  - 注册 `/api/v1/auth/otp:send`、`/api/v1/auth/otp:verify`、`/api/v1/auth/token:refresh`。
  - 保留 `bffkit.TraceFilter`、`bffkit.IdempotencyFilter` 和 `bffkit.ErrorEncoder`。

### Error Mapping

| Applicant / BFF condition | Public code | HTTP | Frontend state |
|---|---|---:|---|
| `unsupported_country` | `unsupported_country` | 422 | 手机号字段错误 |
| `otp_cooldown_active` | `otp_cooldown_active` | 429 | 发码冷却 |
| `code_invalid` / `otp_code_invalid` | `code_invalid` | 422 | 验证码不正确 |
| `code_expired` / `otp_code_expired` | `code_expired` | 422 | 验证码过期 |
| `too_many_attempts` / locked | `too_many_attempts` | 429 | 暂时锁定 |
| `token_expired` / unauthenticated | `token_expired` | 401 | 回到手机验证范围 |
| Consul no healthy instance | `applicant_unavailable` | 503 | 稍后重试 |
| applicant gRPC unavailable/deadline | `applicant_unavailable` | 503 | 稍后重试 |

如果 `bffkit.ErrorBody` 当前缺少 `retryAfterSec`，实现阶段应以最小兼容方式扩展错误 envelope，确保前端能驱动冷却 / 锁定倒计时。

### Consul And gRPC Config

`configs/config.yaml` 增加：

```yaml
applicant:
  consul:
    address: 127.0.0.1:8500
    scheme: http
    service_name: applicant-api
  grpc:
    timeout: 3s
    plaintext: true
observability:
  otel:
    enabled: false
    exporter: otlp
    endpoint: ""
    protocol: http/protobuf
    environment: local
    release: dev
```

`conf.Bootstrap` 增加 `Applicant` 和 `Observability` 配置结构。`plaintext` 仅用于本地/dev；生产环境应由部署配置显式控制。应用代码只依赖 OpenTelemetry 官方 SDK 与官方 OTLP exporter；`endpoint`、headers、environment 和 release 通过环境变量、部署 secret 或本地未提交配置注入，示例文件保持空值。部署可将 OTLP endpoint 指向 OpenTelemetry Collector，再由 Collector 导出到 Sentry；也可在不改应用代码的情况下切换到其他 OTLP 后端。

## Frontend Design

`fides` 保持现有层次：

```text
src/domain/mobile-verification
src/application/mobile-verification
src/adapters/mobile-verification
src/infrastructure/mobile-verification
src/presentation/mobile-verification
src/api/mobile-verification
```

实现策略：

- `RestOtpAuthGateway`
  - 保持 `NEXT_PUBLIC_FIDES_BFF_BASE_URL`。
  - 继续发送 `Idempotency-Key` header。
  - 补充 `refreshToken` 方法，与 application port 对齐。
  - 解析统一错误信封里的 `retryAfterSec`。
- `createDefaultMobileVerificationController`
  - 保留 `mock`、`real`、`disabled` adapter mode。
  - `real` mode 指向 `fides-bff`。
- `MobileVerificationScreen`
  - 已有发码、冷却、OTP 输入、错误展示和成功回调，LEN-43 只补齐真实 BFF 错误和 refresh 场景。
  - 页面不直接 import infrastructure gateway 或 generated proto。
- `BrowserSessionStore`
  - 只保存允许保存的短期会话定位。
  - 不保存 OTP code、完整手机号、access token、refresh token 或 BFF 原始敏感响应。

前端不消费 BFF generated Go/Java contract。前端 REST 形状由 BFF proto HTTP annotation 和 BFF handler 测试保障。

## Data / Config / Permission

- Data model:
  - BFF 不新增数据库表。
  - BFF 不新增 Redis OTP 状态。
  - BFF 幂等先沿用现有 `bffkit` store；若需要跨实例持久化，另起需求或在实现阶段明确为非 master-bound 限制。
- Config:
  - `fides`: `NEXT_PUBLIC_FIDES_OTP_ADAPTER=real`、`NEXT_PUBLIC_FIDES_BFF_BASE_URL=/api/v1` 或目标 BFF URL。
  - `fides-bff`: Consul address/service、applicant gRPC timeout/plaintext。
  - applicant local runtime 可使用用户提供的 PostgreSQL、Redis、Consul 地址。
- Permission:
  - 不新增用户权限模型。
  - Generated Go contract 发布/消费沿用 `idl-go-repo` 权限。
  - BFF 不记录或暴露 refresh token 到日志、指标或 trace attributes。

## Observability

- Logs:
  - Auth endpoint 入口和下游失败记录 `operation`、`error_code`、`trace_id`、`latency_ms`。
  - 禁止记录完整手机号、OTP code、access token、refresh token、challengeId 和 raw request/response。
- Metrics:
  - BFF 记录 auth 请求次数、错误次数、下游调用耗时。
  - 标签限制为 `operation`、`result`、`error_code`、`dependency`。
  - 不使用手机号、applicantId、challengeId、token 作为标签。
- Tracing:
  - `fides-bff` 使用 OpenTelemetry tracing，服务名与服务矩阵保持 `fides-bff`。
  - 应用代码只使用 OpenTelemetry 官方 SDK 和官方 OTLP exporter，不引入 Sentry SDK、Sentry exporter 或 Sentry-specific span processor。
  - trace 默认通过 OTLP 导出到 OpenTelemetry Collector；部署层将 Collector 的 OTLP exporter 指向 Sentry。
  - OTLP endpoint、headers、environment、release / commit 必须通过配置或环境变量注入，不写入仓库。
  - HTTP 入站创建或延续 server span，span name 使用低基数路由模板，例如 `POST /api/v1/auth/otp:send`。
  - applicant gRPC client 创建 client span，span name 使用稳定 RPC 名，例如 `ApplicantAuthService/SendOtp`。
  - applicant gRPC client 注入 W3C TraceContext，不向下游传播内部敏感 baggage。
  - Consul resolution 可以记录 internal span 或结构化日志；失败必须能通过 `trace_id` / `span_id` 串回入口请求。
  - 错误 span 记录稳定 `error_code`，并与统一错误信封和日志中的错误码一致。
  - 脱敏发生在 OpenTelemetry attribute 构建阶段和 Collector processor 阶段；不依赖 Sentry before-send。
  - span attribute 禁止手机号、OTP code、access token、refresh token、challengeId 和 raw request/response。
- Events:
  - 不新增业务事件。

## Rollout And Rollback

Rollout:

1. 合入 / 发布 BFF-facing proto 到 `idl-repo`，生成 Go contract。
2. `fides-bff` 在 LEN-43 branch 使用 RC 或 branch generated contract 验证。
3. 发布 formal Go module tag。
4. `fides-bff` 切到 formal generated Go contract。
5. `fides` 在 dev/local 通过 `NEXT_PUBLIC_FIDES_OTP_ADAPTER=real` 验证。
6. 记录 smoke 和 merge-readiness 证据。

Rollback:

- 前端将 adapter mode 切回 `mock` 或 `disabled`。
- BFF 回滚 auth route/client 变更。
- 若 proto 未 formal 发布，可回滚 proto；若已 formal 发布，不移动 tag，发布后续修正版本。
- applicant-api 无数据或配置回滚。

## Risks

| Risk | Mitigation | Owner |
|---|---|---|
| BFF proto HTTP annotation 与 Kratos 手写路由不一致 | 用 route consistency test 固定三条 path；设计中以 proto 为事实源 | BFF |
| generated Go contract formal 版本不可用 | IDL task 和 generated contract task 独立，master-bound 前必须有 formal tag 证据 | Platform |
| Consul 本地服务名和 dev/prod 服务名不一致 | 服务名配置化，测试覆盖无实例和不可用 | BFF |
| `bffkit` 错误信封无法表达 `retryAfterSec` | 最小扩展 envelope，保持旧字段兼容 | BFF |
| 前端保存敏感 token 或 OTP | session store 测试和 review 检查，不持久化敏感内容 | FE |
| applicant-api local runtime 未就绪 | 用 applicant gRPC test server 做 integration，真实 smoke 记录 blocker | Backend / BFF |

## Open Decisions Before Implementation

| Decision | Default | Blocking If Different |
|---|---|---|
| `Idempotency-Key` 是否放入 BFF proto body | 不放，保持 HTTP header 横切语义 | 如果要求 body 字段，需要同步前端、BFF 和 applicant 映射 |
| `RefreshToken` 是否接入页面自动刷新 | 本需求补齐 gateway/BFF 入口，页面自动刷新只做最小 session-expired 行为 | 如果要求完整自动刷新策略，需要补前端会话生命周期设计 |
| BFF 幂等 store 是否需要 Redis | 沿用现有 memory store 作为本地/dev，master-bound 持久化另起风险或任务 | 如果要求生产多实例幂等，需扩展 BFF data 层和配置 |
